# Slash commands: research and reconstruction contract

Research date: **2026-10-28**. Target: recovered **mig33 Java ME v4.62 build .000**, with private messages and public rooms first. The eleven core commands below are implemented in the Go compatibility server. Gift commands, Group-linked administration and bounded local bots are also implemented under their explicitly scoped contracts. The historical evidence and reconstruction choices are recorded separately here.

## What the additional research establishes

The original v3 and v4 clients recognize a leading slash without enumerating commands. They suppress local echo and send the text through ordinary500. The command names and historical responses came from the server, so a client decompilation cannot recover a complete command registry. See [the original-client inference audit](../research/applets/shared/backend-inferences.md#slash-prefixed-text-suppresses-local-echo).

A **19 March2010 first-person account** describes using commands in rooms and private chat. It documents `/me` followed by free text, `/roll` without arguments, and `/hug username`, including targeting one's own name. It gives the observed output fragments “will be right back” and “rolls 98”, and describes brown action text. This supports the basic action mechanism and examples; one observed roll of98 does not establish the random-number range. [Naphee's contemporary account](https://khusnullutfi.wordpress.com/2010/03/19/command-text-code-buat-chatting-di-mig33/).

A **5 February2011 guide** reports that `/fortune` and `/8ball` generated varying responses. It says presentation changed over time to include the invoking username. The guide supplies no complete response bank, random distribution or definitive protocol payload. Its claimed red text should not override the recovered client's theme behavior. [Contemporary emote guide](https://geeknepal.wordpress.com/2011/02/05/mig33-emote-command/).

A **December2013 compilation** supplies example output for some emotes and distinguishes forms with and without a target. Its author explicitly adapted material from other sites, and it postdates this target period. It is a useful corroborating lead, not proof of exact4.62 wording. Its sources at `etrick33.wapka.mobi/site_130.xhtml` and `mynepalwap.wen.ru/mig33/migemotes.html` were not retrievable in this pass. The compilation also contains inconsistent spelling and an apparent self/target substitution error for `/cry`. We therefore do not copy it wholesale or label the replacement templates historically exact. [Later compilation](https://blackenzeru.blogspot.com/2013/12/mig33-commands-list.html).

### Recovered native action rendering

The most useful additional finding is in the original renderer. Incoming500 content type `6:S6`, when body-color tag13 is absent (or−1), takes a special path:

1. Select action color through `y.a(5,theme)` → `bj.l()` → theme field148.
2. Suppress the ordinary sender-name/colon prefix.
3. Suppress the display-picture prefix.
4. Render the complete supplied action body.

The bundled/fallback color is `10040064` (`#993300`, brown). This matches the2010 observer's color description. It is a confirmed renderer contract, and the original-client acceptance run verifies the resulting action presentation. Do not send an explicit body color, which bypasses that special branch, or misuse unexplained tag14 as an emote flag.

Evidence: [s.java](../research/applets/v4/artifacts/normal-flow/s.java), lines645–650; authoritative [s.txt](../research/applets/v4/artifacts/bytecode/s.txt), method `a(int,String,String,String,short,int,int,String,boolean,String,int)`, offsets84–111; [y.java](../research/applets/v4/artifacts/normal-flow/y.java), `a(int,bj)` at1245; [bj.java](../research/applets/v4/artifacts/normal-flow/bj.java), `l()` at1809. The [500 dispatcher](../research/applets/v4/artifacts/normal-flow/bc.java) passes content tag6 into the conversation model. User commands remain outgoing content type1; type6 is generated by the server.

## Core command contract

The following eleven names form the current implementation scope. Their existence is historically documented; the complete templates, validation rules and random policies below are explicit local reconstruction choices unless separately identified above.

| Command | Arguments | Intended result |
| --- | --- | --- |
| `/me text` | Required nonempty action text | Actor's authenticated username followed by the text |
| `/hug [username]` | Optional one target | General hug action or a hug directed at the target |
| `/slap [username]` | Optional one target | General slap action or a slap directed at the target |
| `/wave [username]` | Optional one target | General wave or a wave directed at the target |
| `/smile [username]` | Optional one target | General smile or a smile directed at the target |
| `/laugh [username]` | Optional one target | General laughter or laughter directed at the target |
| `/cry [username]` | Optional one target | General crying or a crying action involving the target |
| `/brb [username]` | Optional one target | An away-for-a-moment action; the untargeted phrase is supported by the2010 account |
| `/roll` | None | One random integer from1 through100, inclusive; this range is local policy, not recovered fact |
| `/fortune` | None | One entry from a small replacement response bank |
| `/8ball` | None | One entry from a small replacement response bank |

The replacement banks and ordinary emote wording are functional stand-ins, not recovered historical content. Command matching is case-insensitive as a local convenience; the historical case rules were not established. Extra arguments to no-argument commands and multiple target tokens are invalid. `/me` preserves its argument text after ordinary leading/trailing whitespace handling.

An optional target must be a registered account and must belong to the conversation's audience: a currently present member for a room, a current member for a private group, or the peer/self for a private conversation. A targeted emote does not open or send to a different conversation. Self-targeting is allowed. These validation boundaries are local policy; the2010 account establishes self-targeting but not every historical membership or presence edge case.

## Generated text and delivery

The following templates are local replacements except the recorded untargeted `/brb` phrase. Every result begins with the authenticated actor; targeting does not change the sender or move the message to another conversation.

| Command | No target | Target `bob` |
| --- | --- | --- |
| `/hug` | `alice hugs everyone.` | `alice hugs bob.` |
| `/slap` | `alice slaps their forehead.` | `alice slaps bob.` |
| `/wave` | `alice waves.` | `alice waves to bob.` |
| `/smile` | `alice smiles.` | `alice smiles at bob.` |
| `/laugh` | `alice laughs.` | `alice laughs with bob.` |
| `/cry` | `alice cries.` | `alice cries on bob's shoulder.` |
| `/brb` | `alice will be right back` | `alice will be right back, bob.` |

`/me is back` becomes `alice is back`; `/roll` becomes `alice rolls N`. `/fortune` and `/8ball` prefix the actor and command name to a response selected from the small replacement banks in [commands.go](../internal/chat/commands.go). Random selection uses Go's cryptographic random source. Both roll bounds and response banks are local choices; retries of an already stored result never reroll it. Resending the command as a new500 request remains a new message and a new draw.

The original320-character composer remains intact. The server accepts up to65,536 UTF-8 bytes, with a second bound after adding the actor to generated text. Unknown commands, unsupported commands, invalid arguments and permission failures return correlated opcode0. They create no message/history entry and broadcast no raw slash text. Incoming content6 is rejected: only the server generates that presentation. Slash moderation returns an explanation directing users to the native menus where applicable; `/help` currently receives the supported-command list through the same unsupported-command error.

## Delivery and validation guarantees

- Authorize the original conversation and sender before a generated action can be stored or delivered. Room membership, room mutes, group membership and personal blocks still apply.
- Derive the actor from the authenticated session. Client-supplied sender fields and text must not impersonate another user or a system actor.
- Persist the generated action and its content type, rather than only the original slash text. A retry of delivery must retain the chosen roll/result; replay must not generate another random value.
- Return the action to the originating client because it deliberately omitted local echo. Other recipients receive the same generated content through the conversation's usual delivery policy.
- Emit incoming500 content6 without tag13 so the original renderer supplies action styling and avoids a duplicated `username:` prefix.
- Return an explicit error for unknown, malformed or unavailable commands. Do not acknowledge them while silently forwarding their raw slash text to other users.

These requirements do not add read receipts, exactly-once guarantees or a new web endpoint. The command enters through the existing message500 operation on either TCP or the HTTP tunnel. Existing transport-delivery and offline-history boundaries still apply; see [chat behavior](chat.md).

Schema8 adds a boolean `messages.action`, default false for existing messages. The history API returns `"action":true` for generated actions and retains the true authenticated `sender`, canonical conversation, generated body and stored creation time. Ordinary messages retain their existing shape. No historical database schema or new native metadata field is being claimed.

Private/group action audiences include the author for delivery because the original sender supplied no local echo. They use the same durable outbox, including retry after failed writes or restart. Currently active sessions of an account can receive the action; transport acknowledgment remains account-scoped. Ordinary text now also copies to other active sessions, while the originating native client retains only its local echo. Room actions include the sender's joined sessions in live delivery and never enter offline replay. A room command is rejected before commit if its originating session has no queue space, even if another session of the same account has space.

An incoming private500 is routed using tag2/contact5; the original client ignores destination4 for choosing the peer tab. Consequently, an author's own private-action result uses the destination peer in wire tag2/contact5 so it returns to the correct existing tab. Its expanded body and saved history still identify the true actor. The backend's delivery metadata retains that actor for block enforcement and buffered-message cancellation, so blocking a peer cannot accidentally suppress one's own result. Recipient-facing packets continue to use the actual actor in tag2.

Tests: [server command flows](../internal/realtime/commands_test.go) and [migration/audience persistence](../internal/adapters/sqlite/repositories/actions_test.go).

## Gift commands

The [original19 January2011 author guide](https://mig-info.blogspot.com/2011/01/mig33-new-command-gift-on-chat.html) documents discovery, send and rating commands. The local implementation uses those names against the recovered-name/replacement-artwork catalog. Command responses are visible only to the requesting native session in its current private, group or joined-room tab; they are not broadcast or saved as conversation messages. A completed purchase separately creates the existing durable private gift receipt for sender and recipient. The response wording, native action presentation, prices and selection order are local choices.

| Command | Local behavior |
| --- | --- |
| `/gift` | Show discovery, sending and rating help. |
| `/gift list` | List gifts in local alphabetical order, with test-credit prices. |
| `/gift new`, `/gift featured`, `/gift popular` | Explicitly labeled local alphabetical views; original release, featured and popularity rankings remain unavailable. |
| `/gift search TEXT` | Case-insensitive name/description search. |
| `/gift display NAME` | Exact case-insensitive name or catalog ID lookup, description, category, local price, artwork provenance, mean/count and own rating. |
| `/gift category [NAME]` | List catalog categories or gifts in the selected category. Unrecovered placements remain local choices. |
| `/gift gifts` | List the authenticated user's received gifts and attached notes, newest first, from the owned-gift ledger. |
| `/gift USER NAME [-m MESSAGE]` | Purchase for an existing recipient with local test credits; atomically commit debit, inventory, optional note and private gift message. Name or catalog ID accepted. |
| `/gift rate NAME RATING` | Save one current vote per account/gift. A later vote replaces it. The integer1–5 scale is explicitly local; the original screenshot establishes a decimal mean but not the exact accepted scale or repeat-vote policy. |

Responses contain at most20 rows and a bounded3500-character body, with Store guidance for further entries. Group membership and current room membership are checked; a full requester's native queue fails before mutation. A full or offline recipient queue does not undo a completed gift: durable delivery resumes on polling/login. Recipient existence, chat privacy and directional blocks apply; privacy/block checks are repeated inside the debit transaction. Notes are literal text, at most320 UTF-8 bytes, without control/format characters or reserved gift/photo/pack triggers; emoticon ownership remains checked. Web pages escape note text through templates. JSON/WAP message composers exclude native gift controls and use catalog/page APIs instead. Formatted markup beginning with `/gift` remains authored text.

Sending reuses the native provider nonce: the SHA-256-derived key includes the complete original packet and current session ID. Exact retries during that session return the same receipt without another charge, note, inventory item or message. Changing any packet field or logging in again creates a new purchase request; the original protocol provides no stable cross-session purchase key. Store calls with an explicitly reused nonce reject changes to recipient, product, amount or note. Empty notes preserve old Store receipts/replay. Ratings retain one current persisted vote, so repeating a vote does not inflate the count; submitting an earlier value again replaces the current value.

Native acceptance found that the original Canvas text renderer consumes newline characters without adding visible spacing. Generated gift responses therefore use ordinary spaces and semicolons between entries; new gift receipts separate `Message:` with a space. The stored note itself remains unchanged, and existing messages are not rewritten.

Tests cover all three chat kinds, requester-only confirmations, private gift delivery, inventory/note authorization, invalid input, bounded output, exact packet retries, concurrent ledger retries, recipient backpressure/offline delivery, privacy/blocks/membership, transaction rollback, restart, schema17 upgrade, unchanged legacy receipts and one-vote rating aggregation.

## Commands that need a different scope or more evidence

Group-linked moderation commands cannot be treated as aliases for every ordinary public room. Historical2011 documentation distinguishes community Group-owned rooms from Global Chat Rooms and describes owner/moderator permissions. Those community Groups are different from our private group conversations. [Group-room command documentation](https://pakmig33.wordpress.com/2011/04/05/group-chat-room-commands/).

In particular, `/kick` also appears in football-emote lists. A **29 June2010 announcement** reports a text kick command, and a same-day Indonesian report explicitly associates it with admins/moderators. Those reports do not establish ordinary-user text voting, precise room eligibility or suspension duration. The detailed2011 Group-linked documentation instead describes a one-hour suspension across the community Group's linked rooms, a model absent from our ordinary public rooms. [2010 announcement](https://mig33-news.blogspot.com/2010/06/new-kick-command.html), [same-day report](https://narutogakure33.blogspot.com/2010/06/).

Mapping `/kick` directly to the existing706 vote/kick service without choosing a context rule would invent semantics. Slash `/kick`, `/mute` and `/unmute` remain unavailable with explanatory errors. Group-linked silence/lock/ban/announcements/descriptions/invitations and bounded local dice/8ball bots now have explicit local semantics in the [Group-room contract](room-completion.md). Existing native kick/vote and Room Info mute/unmute controls remain the supported room moderation paths. The full historical emote catalog also remains broader than the eleven-command core above.

An additional28 October2026 recovery found original migGames help visibly listing `/games`, `/bot <game>` and `/bot stop` in a [2009 client capture](../research/applets/v4/artifacts/historical-games/games-2009-2.png). `/games` now returns the local/reference catalog privately to a native participant in a joined room, and `/bot stop` aliases the existing authorized Group-room stop action. Twenty catalog names and three announced partner games are recorded with provenance in [games-history.json](../research/applets/v4/docs/data/games-history.json); their complete mechanics are not reconstructed. See [catalog availability and command scope](room-completion.md#recovered-game-catalog-and-explicit-placeholders).

Unrecovered details include the exact4.62 response catalog and punctuation, `/roll` range/distribution, random response banks, per-command target requirements, command-case rules, fees, cooldowns and every moderation context. The code and acceptance results should state local choices explicitly rather than presenting those gaps as historical facts.

## Expo command discovery

Expo bundles a generated command catalog for local editing assistance. Its source
is [internal/slashcommands/catalog.go](../internal/slashcommands/catalog.go),
projected by the existing Go contract generator into
[slash-commands.ts](../apps/mobile/src/mig33/generated/slash-commands.ts).
The catalog describes this server's implemented behavior: 27 root entries and
13 gift/bot forms. It is deliberately separate from the recovered wire registry.
There is no discovery endpoint, additional packet field or new operation.

A leading slash opens suggestions while the caret is in the command token.
Filtering is case-insensitive; the known gift/bot families also complete their
second token. Selection replaces the command span, preserves existing argument
text and focuses the editor. It does not send anything. Generic gift sending
inserts `/gift ` for a recipient, never an invented `/gift send` command.
The user can dismiss suggestions or send unlisted commands normally.

Private and private-group chats offer only applicable commands. Joined rooms add
room commands; community-linked rooms additionally expose the community forms.
Known room mute state hides commands that the server disallows while muted.
Community owner/moderator authority, silence and active-bot state are not fully
observable from the original packets, so requirements are described rather than
guessed. Room moderator status is not treated as community authority. The server
remains authoritative. `/kick`, `/mute`, `/unmute` and `/help` are excluded because
they currently return explanations rather than implementing those slash actions.

Catalog checks exercise existing parsers/dispatch coverage; pure editor tests
cover context, caret positions, aliases, stale taps, preserved suffixes and the
320 UTF-16-unit bound. The focused iOS `--commands-only` workflow checks both
original transports, unsent insertion, gift completion and real private/room
action delivery. See [the native runner](../tools/mobile/README.md).

## Validation

`go test -race ./...` and `go vet ./...` passed. Regression coverage includes all eleven command names, canonical targets, permission failures, unknown/unavailable commands without side effects, forged incoming content6, ordinary text behavior, buffered block changes, full sender queues even with another active session, durable sender/recipient actions and unchanged random output after a failed HTTP write and restart. Schema7→8 tests preserve old message IDs, bodies, colors, audiences and sequence values.

The [unchanged original-client acceptance run](../research/acceptance/v4/slash-result.md) passed four JVM phases: Alice/TCP, Bob/HTTP and Carol/TCP together, followed by a fresh returning Bob/HTTP. It captured68 screenshots and227 binary frames. Every command uses the original Write/TextBox/Send handler, exercising native suppression of slash local echo. Captures and transcript assertions verify prefix-free action rendering, one result per client, correct private peer tabs, group routing, unavailable-command errors and offline replay.
