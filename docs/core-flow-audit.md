## Defects found in implemented behavior

### 1. Multiple sessions produced inconsistent presence

**Priority: P1. Status: corrected; focused race-enabled regression tests passed.**

Previously, `Server.presence` returned the first visible session found in a Go map. Opening two sessions for the same account with different presence values could therefore make roster snapshots, profile queries and broadcasts disagree without a user changing anything.

Evidence: [application.go](../internal/realtime/application.go), `presence`. Native presence values are documented in [the v4 protocol](../research/applets/v4/docs/protocol.md): online1, busy3, away4, invisible/offline99.

The correction gives visible sessions deterministic precedence: online, then busy, then away; only invisible or expired sessions resolve to99. This precedence is an explicit local multi-session policy, not a recovered historical server rule. [Presence regression tests](../internal/realtime/presence_test.go) cover mixed-presence sessions, invisibility, removal of a visible session and replacement of an online session while another busy session remains.

### 2. HTTP expiry and reauthentication could leave contacts showing a stale presence

**Priority: P1. Status: corrected; focused race-enabled regression tests passed.**

`active` removed an expired session, but `removeSession` previously did not broadcast presence. TCP disconnect and logout broadcast separately, so ordinary tests of those paths passed. An expired HTTP session removed during a later request or login sweep could leave another connected user's cached contact online. Replacing an authenticated session with a new challenge had the same gap if authentication then failed.

Evidence: [application.go](../internal/realtime/application.go), `active` and opcode200; [delivery.go](../internal/realtime/delivery.go), `removeSession` (line33). The native contact-state update is404, handled in the [original receive dispatcher](../research/applets/v4/artifacts/normal-flow/bc.java).

The correction broadcasts after removing any authenticated session, using the remaining sessions to calculate presence. A [background expiry sweep](../internal/realtime/presence.go) runs from the explicitly supervised `Coordinator.Run(ctx)` loop and stops when that loop is canceled or the coordinator closes, so HTTP clients that disappear without another request are eventually removed. Session idle expiry remains two hours and unauthenticated challenge expiry remains one minute. Sweep scheduling, cleanup and shutdown share the coordinator mutex; the lifecycle owner joins the maintenance loop before repository cleanup.

The focused tests cover HTTP-session expiry, room departure, replacement of an authenticated session, failed replacement authentication, and continued visibility of another live session. They invoke the expiry helper directly rather than waiting30 seconds; the timer lifecycle was independently reviewed. The targeted `go test -race` run passed for all three presence regression tests.

### 3. A full queue can truncate private-group restoration

**Priority: P2. Status: corrected; race-enabled queue and membership regression tests passed.**

Previously, `restoreGroups` returned when the128-packet session queue was full, and the first contact sync marked the session ready without retaining omitted notices. A later poll could not resume those memberships.

The server now snapshots pending group IDs per session and resumes as transport space becomes available. It reloads current membership before each deferred notice, skips groups left in another session, and retains the existing transport-boundary check for notices already buffered when a leave occurs. Restoration precedes queued group text. It retries a failed initial store read instead of treating it as an empty snapshot.

[Delivery implementation](../internal/realtime/delivery.go) and [regression tests](../internal/realtime/group_restoration_test.go) cover257 memberships, queues occupied by0/1/127/128 other packets, repeated contact sync without duplicated notices, offline group-text ordering, cross-session leave and changed member lists. Notices remain transient controls; this fix does not add message receipts or guaranteed replay of a notice after a failed transport write.

There is a separate native UI constraint: [k.java](../research/applets/v4/artifacts/normal-flow/k.java):687 adds tabs only while the existing total is at most25, permitting26 total including base tabs. Fixing the backend queue does not make129 native tabs possible. Large stored membership sets need a directory/reopen design or a deliberate compatibility limit. The corrected queue defect could also affect smaller sets when other traffic occupied the queue.

## Reconnect behavior: an important documentation correction

The server correctly treats public-room membership as session scoped and does not replay missed room traffic. However, **the original client automatically submits703 for retained room tabs during its reconnect path**. “Rooms always require manual rejoin after reconnect” is too broad.

The original chain is [bc.java](../research/applets/v4/artifacts/normal-flow/bc.java):2021, successful203 with `u.aC` set → [k.java](../research/applets/v4/artifacts/normal-flow/k.java):106, `f()` iterates type5 room tabs → [aj.java](../research/applets/v4/artifacts/normal-flow/aj.java):6033, `b(room,true)` → `bc.a(room,false)` at386, which constructs703. This is a client request, not persistent server membership. A fresh application session with no retained tabs has nothing to rejoin. Native acceptance now covers successful automatic rejoin, full-room and ban rejection, unban recovery, kick notification/retained tab, denied sends and later rejoin. See [29-screen/312-frame result](../research/acceptance/v4/reconnect-result.md).

Keep the backend rule, and distinguish a fresh login from reconnection with retained tabs in user-facing help and [chat](chat.md), [rooms](rooms.md) and [status](target-and-gaps.md) documentation. A synthetic login test that does not retain the native tabs cannot establish the full reconnect UX.

## Checked distinctions and remaining uncertainties

- **Room mute is not personal block.** The stock “Block & Mute User” action sends417, with no room identifier. It does not exercise the implemented moderator709 room-mute handler. Joined moderators now have explicit member mute/unmute forms in Room Info; native marked-user unmute and kick paths also remain available. See [the implementation boundaries](target-and-gaps.md#compatibility-boundaries).
- **A kick is not a ban.** Membership removal alone permits immediate rejoin. Persistent room bans now prevent re-entry until an authorized unban, separately from706. The original receive dispatcher still has no established room-only forced-close packet; its retained tab and next-send error are compatibility limits, not evidence of a failed kick. Ban duration and Group-wide policies are not inferred from the native kick menu.
- **Contact deletion has two native presentations.** The requester's ACK406 branch in `bc.java`:1443 removes the contact; the incoming406 branch at2377 also closes that contact's private tab. The server uses these existing paths for the initiating and other sessions. Do not invent an alternative reply simply to make their UI effects identical.
- **Contact approval remains uncertain.** Directed address-book additions are the current local contract. This v4 build does not contain concrete outgoing413/414/415 builders. The mere word “Friend” does not establish the original server's reciprocal request/accept policy.
- **Slash commands are not recovered API definitions.** The native composer suppresses local echo for slash-prefixed text but still sends500, implying server feedback. A further research pass established an eleven-command core with documented replacement templates/random rules. Generated results now use the recovered content6 renderer and return to the sender; unsupported slash text produces errors without broadcast. See [command evidence and implementation](slash-commands.md). Community Group pages establish a separate membership/link model. Local Group-linked controls and bounded bots are now implemented; their historical policies and football `/kick` overlap remain unresolved. See [room completion](room-completion.md). The explicit native room706/709/710 operations have stronger evidence.
- **Multi-session synchronization now has an explicit local contract.** Ordinary sends copy to other active author sessions, with peer-routed action styling for private native copies. JSON sync/history pagination, durable send idempotency and private read positions support the later frontend. Native recipient delivery remains account scoped; a full secondary recipient recovers missing messages through JSON sync rather than an invented legacy history opcode. See [chat contract](chat.md).
- **Queues and live controls have distinct guarantees.** Durable private/group text retries after transport failures. Presence, group notices and room control text use transient bounded queues. The group-restoration truncation above is corrected without changing transient notice semantics; general delivery/read receipts and exact-once behavior remain separate features.
