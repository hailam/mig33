# Original-client public-room integration

The [recorded room acceptance result](room-report.md) passed with all three original clients. The separate [moderation run](ROOM_MODERATION.md) and [passing result](room-moderation-report.md) cover kicks, mute/unmute, participant icons and the original kick-notification popup.

With the local backend running on its default ports, execute:

```sh
sh tools/applets/v4/integration/run-room.sh
```

Three unchanged v4.62 clients run in separate JVMs: Alice and Carol use the original TCP transport, and Bob uses the original HTTP tunnel. Their accounts use passwords `<username>-demo`. The script verifies the original JAR, compiles the harness, gives each client isolated temporary storage, waits for all assertions and cleans up the JVMs. Successful clients send the original 300 logout and wait for its acknowledgment before exiting. Each step has a 60-second deadline. Evidence is written only to `room-out/`; existing private and group acceptance evidence is preserved.

## Sequence and assertions

1. Each client receives categories through 713/714/715 and refreshes the category with the original 716 builder. The original catalog must contain Lobby, Gaming and Help from 701 records followed by717. The room list is rendered and its original model values saved.
2. Alice and Bob join Lobby. Carol joins Gaming. Each original 703 must receive701 followed by its matching opcode1 acknowledgment. The original room tab must be ready and the pending 703 must be gone.
3. Alice's original 707/708 participant popup must show Alice and Bob. The original catalog must display Lobby 2/50 and Gaming 1/50. Carol's Gaming participant popup must show only Carol.
4. Alice sends Lobby text using the original 500 builder with conversation type3. Bob must render it. Carol's captured incoming room packets must not contain that Lobby text. Her attempt to send to Lobby without membership must receive a correlated opcode0 rejection.
5. Carol joins Lobby. The original Lobby participant popup must now show all three users and the catalog must display3/50. Alice, Bob and Carol exchange room text; every intended recipient must contain the expected text in the original room renderer's wrapped rows and a matching received500 frame.
6. Carol leaves Lobby using the same original operations as the close-room branch: add the room to the pending suppression list, queue704, remove the original tab and close menus. Its acknowledgment must clear suppression, and the tab must be removed.
7. Carol's subsequent Lobby send must receive a correlated opcode0 rejection. Alice's participant popup and catalog must return to two Lobby members. Bob receives Alice's final Lobby message; Carol must not receive its room500 packet. Carol's successful Gaming participant request verifies that her other room membership remains active.

## Original-client details that affect compatibility

The correlated701 for a703 join creates or updates the room conversation but does not complete the pending request. The following opcode1 marks the room ready and clears703. Returning only701 leaves part of the original join flow incomplete.

Category1 starts collapsed. The harness invokes the original category-expansion method before calling the original refresh method; a collapsed category intentionally produces no716 request.

Room-list701 records require the room name, capacity, occupancy and category ID.717 finishes the request for the category from pending 716. Public-room participant708 shares the group755 popup parser; its usernames are semicolon-terminated entries.

The original client can create an unjoined room tab to display a rejected send. It can also buffer room text until the room has been joined. Consequently, absence of rendered text alone is not sufficient evidence that an outsider received nothing: the harness also decodes captured500 frames using the original packet parser and checks destination, conversation type and body.

The leave test removes Carol's Lobby tab as the original close-room flow does. Its deliberately rejected post-leave send may create a fresh unjoined error view. That does not rejoin the room on the server.

## Evidence and scope

`room-out/<username>/` contains runtime logs, packet-event TSV, exact binary frames, original model text and Canvas screenshots. A client's `result.txt` appears only when its entire sequence passes. Catalog snapshots include actual occupancy text generated by the original client. Participant screenshots come from the original 708 popup, not a recreated list.

This runs the original application classes and local network transport. Reflection invokes the original methods and selects tabs; it does not automate keypad input. Screenshots use MicroEmulator fonts and a 240×320 Canvas with local test accounts and fixture room names. No legacy external service is contacted. The existing [runtime boundary](README.md#runtime-boundary) applies.

These rooms use conversation type3. Private groups use type2 and have a [separate acceptance run](GROUPS.md). Room membership is scoped to the server session; this harness does not claim automatic room rejoin or historical message replay. Storage and reconnect policy have separate Go tests.
